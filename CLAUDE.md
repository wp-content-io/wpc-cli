# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Role

`wpc` — the **CLI tool** of wp-content.io. It builds plugins/themes and pushes them to the API from a terminal or from CI. It is a client of the wp-content.io registry API (see "Product context" below).

Stack: **PHP 8.2**, **Symfony Console 7**, Guzzle (HTTP), Slugify. Distributed as a self-contained **`.phar`** binary (`wpc.phar`), and as the Composer package **`wpcontent/wpc-cli`** (`composer global require`).

## Product context

`wp-content.io` is a SaaS for distributing and updating **private WordPress plugins and themes** outside the official directory (public docs: https://docs.wp-content.io/, CLI reference under https://docs.wp-content.io/cli). This repository is only its command-line client: the registry API it talks to (default `https://registry.wp-content.io`), the web dashboard where accounts and API keys are managed, and the WordPress plugin that installs updates on end users' sites are separate products and **not open source**. A CLI feature that needs data the API does not expose yet cannot be built here alone — open an issue first.

The CLI authenticates with an API key sent in the **`x-api-key`** header. The registry also knows *bundles* (shown as "Starter Packs" in the dashboard); they are deliberately **not exposed by the CLI**.

## Commands

```bash
composer install                  # also installs isolated build tools (composer-bin-plugin)
php bin/wpc                       # run the CLI in dev (management commands + global options)
php bin/wpc plugin                # the verbs of one namespace
php bin/wpc plugin list

composer test                     # PHPUnit
composer analyse                  # PHPStan (level 6)
composer cs                       # PHP-CS-Fixer (dry-run); composer cs:fix to apply
composer box -- compile           # build wpc.phar (Box, configured in box.json)
```

> **Build tools are isolated** with `bamarni/composer-bin-plugin` in `vendor-bin/` (Box, PHP-CS-Fixer), keeping their own dependency trees out of the phar's `vendor/`. The versioned `wpc.phar` is the release artifact; its version is injected by Box from the git tag (`@cli_version@` → `git-tag: cli_version` in `box.json`). Box needs a tag reachable from `HEAD`: CI checks out with `fetch-depth: 0`, and `.github/workflows/ci.yml` stamps `dev-<sha>` through a throwaway `box.ci.json` when there is none (a version `Update\Version` reads as unknown); the release workflow has no such fallback.

> **Releases** (`.github/workflows/release.yml`, on every `v*` tag). Tags are `vX.Y.Z`, pre-releases `vX.Y.Z-beta.1`/`-rc.1`; the published *version* is the tag without its `v` (manifest, storage path, Docker tags). The workflow builds the phar on PHP 8.2, attests its provenance and creates the GitHub Release (`wpc.phar` + `wpc.phar.sha256`, marked prerelease for a pre-release tag); the publishing jobs then wait for approval in the **`release` environment**. They push one multi-arch Docker image per PHP version (8.2–8.5) to Docker Hub `wpcontent/wpc-cli` and `ghcr.io/wp-content-io/wpc-cli`, and upload `<version>/wpc.phar` + `.sha256` to the download storage behind `https://downloads.wp-content.io/wpc-cli/`. **Only a stable tag that is the newest stable tag moves the mutable channels**: storage `latest/` and Docker `:latest`/`:php8.x`. A pre-release publishes its versioned objects only, so `self-update` and `:latest` pipelines never pick it up. On `latest/`, the order is fixed — `wpc.phar`, then `wpc.phar.sha256`, then `manifest.json` (`{name, version, sha256, url}`, `url` = the GitHub asset, checked to resolve and to match the sum first) **last**. The `latest/wpc.phar` pair must keep being published: clients up to 2.0.0 do not trust a GitHub pin and fall back to it.

> `box.json`'s finder ships `vendor/**/*.php` **plus** `symfony/console/Resources/*.{bash,zsh,fish}` — Symfony 7's `completion` command scans that directory at construction time, and a phar missing it fails on every single invocation.

### Configuration (resolution order)

Handled by `src/Config.php`, global options declared in `src/Application.php`:

- `--repository=<url>` or `WPC_REPO_URL` env var (default `https://registry.wp-content.io`)
- `--api-key=<key>` or `WPC_API_KEY` env var
- `--output=human|plain|json` (default `human`). An unknown value is now rejected instead of silently falling back to `human`.

### Output modes

| Mode | Rendering |
| --- | --- |
| `human` (default) | **Interactive** when attached to a real terminal, otherwise identical to `plain`. |
| `plain` | The static Symfony tables. Forces the non-interactive rendering on a terminal. |
| `json` | Raw machine output — the automation contract. Never decorated, never interactive. |

`human` only upgrades to the TUI when every check in `src/Tui/Environment.php` passes: interactive input, verbosity above quiet, decorated output, a `ConsoleOutputInterface`, stty available, stdin **and** stdout are TTYs, and neither `CI` nor `WPC_NO_TUI` is set. Anything else (a pipe, `-n`, `-q`, `--no-ansi`, CI) falls back to the static tables, so no existing script changes behaviour.

The format is the *other* half of that decision, and it is resolved in one place: `Runtime::isInteractive()` is `Config::allowsInteractive() && Environment::supportsInteractive()`, settled once in `Application::doRun()` and shared by every command. Everything that would take the screen over — the tables, `StepProgress`, the `init` wizard — reads it, so `--output=plain` really does mean "the static rendering, everywhere". The progress axis is decided next to it, in `AbstractResourceCommand::progress()`: `NullProgress` under JSON, `StepProgress` on a terminal, `PlainProgress` otherwise — the build and the upload go through the same one.

### Streams and exit codes

The other half of the automation contract, pinned end to end by `tests/OutputContractTest.php`:

- **stdout is the answer.** A run that fails writes nothing there under `human`/`plain` — the message goes to stderr, so `wpc plugin build … > artifact.txt` cannot collect a diagnostic where a path was expected. Progress obeys the same rule: `PlainProgress` is built on the error stream, so its steps, its throttled details and its `-v` file list all stay out of the way. It is deliberately not silent — v1 drew a progress bar for every `human` run, TTY or not, and dropping it left a `push` of a large artifact indistinguishable from a hung process, with nothing to keep an output-inactivity watchdog awake.
- **Under `--output=json`, a failure is still an answer**: one object on stdout, `{code, message, errors}`, the same shape for an API error, a build error, a bad option *and* a Symfony error (unknown command, missing argument). `Application::renderThrowable()` is what covers the last one; the contract used to break exactly where a script needed it most. `code` is the HTTP status when there is one and the exit code otherwise — **never 0**, which anything checking the field reads as a success. Every payload is written with `VERBOSITY_QUIET`, because `-q` silences the diagnostics, not the answer.
- **Exit codes**: `0` success, `2` (`Command::INVALID`) the command was called wrongly — missing file, malformed option, unknown command, missing argument — and `1` (`Command::FAILURE`) everything else, an unreachable or unhappy registry included. The same cause gives the same code in every command.
- Failures are `CommandFailure` (`src/Results/`), which `ApiError` and `BuildError` extend. That is what makes the schema single; a new kind of failure only has to pick a parent. **The failure carries its own exit code** (`CommandFailure::exitCode()`, `BuildError::invalidInput()` for the usage ones) rather than each `catch` deciding: that is the only way "same cause, same code" survives being written twice. Symfony's own usage exceptions are folded into the same rule — `find()` rethrows a `CommandNotFoundException` with `INVALID`, and `doRunCommand()` does the same for a missing argument or an unknown option.
- `manifest --get` is the one verb whose human output is a bare value (raw, unstyled, no trailing newline — a shell accessor). Under `--output=json` it is still an object, `{"Version": "1.0.0"}`, and a header that is not there answers **empty with exit 0**, as 1.x did — `VAR=$(wpc … --get "Requires PHP")` under `set -e` must survive a plugin that does not declare an optional header (a 2.0 pre-release made it a usage error; reverted on that ground). The gap is reported on stderr instead, silent under json and `-q`. Two notices, because the parser cannot tell the cases apart: it fills *every* field of the map, with an empty string for the ones the file does not carry, so a misspelled field name and an absent header are detected separately.
- **The configuration is validated in two halves.** `Config::validate()` is what the *invocation* got wrong (a malformed `--output`), fatal wherever it appears; `Config::requirements()` is what a *command* would have needed (a repository, checked by the application for every command; plus, with `$authenticated`, the API key, checked by `AbstractResourceCommand::unmetRequirements()` at the top of `list`, `info`, `push` and `build --push` — after argument validation, before anything is built or sent, exit 2 like the repository; `init`, `build`, `manifest` and `self-update` never ask for it), and `--version` — answered by the parent before any command is looked up — is not held to it. An installer or a CI preflight step checks the binary that way, long before anything is configured.

Authentication uses the **`x-api-key`** header.

### Testing live against a registry

- **Run from source**, not the phar: `php bin/wpc <command>` executes `src/` directly, so every edit is picked up with no `box compile`, and an installed `wpc` phar is left alone. From source, `self-update` and the passive "new version" notice are inert (`Phar::running()` is empty and the version is the `@cli_version@` placeholder). Build a phar with `composer box -- compile` only to test phar-specific behaviour.
- **Point at any registry with a dedicated key.** Precedence is `--repository`/`--api-key` flags > `WPC_REPO_URL`/`WPC_API_KEY` env vars > defaults (`src/Config.php`), so export `WPC_REPO_URL=<registry URL>` and `WPC_API_KEY=<a key created for development>`, or pass the flags.
- The CLI does **not** read a `.env` file (no `symfony/dotenv` at runtime): real environment variables or the flags are required. `.env` and `.envrc` are ignored by `.gitignore` because a file exporting those variables holds a secret — never commit one.

### Command grammar

Commands are `<noun> <verb>`: `plugin list`, `theme push`. **The space is part of the command name** — Symfony's `validateName()` only rejects `::`, so `plugin list` is a legal name, and that is what makes `wpc plugin list --help` print `Usage: plugin list` with no custom descriptor. `src/CommandLine.php` glues the two words the shell passes into that single token before anything binds the input.

Every v1 name (`plugin:ls`, `theme:start`…) is a **permanent alias**, pinned by `CommandContractTest::LEGACY_NAMES` — that list is append-only. Customers' pipelines upgrade themselves through `self-update`, so removing one is a silent breakage on someone else's machine. Typing an alias prints a deprecation notice on stderr; unlike the update notice it does *not* require a TTY and does *not* switch off in CI (that log is the only channel that reaches whoever maintains the pipeline), but it stays silent for `--output=json`, `-q`, and `WPC_NO_DEPRECATED_WARNING=1`.

The same goes for v1's **`--paged`** on the list commands (now `--page`, `-p` unchanged): pinned by `CommandContractTest::LEGACY_OPTIONS`, same notice rules. It is deliberately **not** in the definition — Symfony has no hidden option, and anything declared shows up in `--help`, the listing, the completion and the contract fixture — so `Application::renameLegacyOptions()` rewrites the token once the command is resolved, before it binds its input.

## Architecture

- **`src/Application.php`** — extends `Symfony\Console\Application`. Registers every command **with its collaborators**, adds the global options, resolves the `Runtime` in `doRun()`, and emits the passive "new version available" and "deprecated name" notices on stderr. Also overrides `run()` (argv merging), `find()` (near-misses inside a namespace, which Symfony only looks for across `:`), `extractNamespace()` (the namespace is the word before the space — without it every canonical name fell into `_global`, and `wpc list plugin --raw` came back empty), `complete()` (one word at a time) and `renderThrowable()` (the JSON contract on the error path). It no longer holds the HTTP client or the display logic — those are `RegistryClient` and `OutputRouter`.
- **`src/Runtime.php`** — the resolved `Config` plus "may this run take the terminal over". It exists to break an ordering problem: commands are constructed when the application is, but the configuration only exists once an input has been parsed. Every accessor answers with the documented default until then, so a caller reached before resolution — rendering an exception thrown while parsing — behaves rather than fails. Resolution happens **before** `find()`, otherwise a mistyped command name is rendered without knowing the output format.
- **`src/Env.php`** — the one reader of the environment (`$_ENV`, `$_SERVER`, then `getenv()`). There used to be two, and they disagreed: `putenv()` is invisible to the superglobals, and the superglobals depend on `variables_order` — so `WPC_NO_TUI` was honoured where `WPC_API_KEY` was not, depending on how each had been set.
- **`src/CommandLine.php`** — the grammar parser: pure, static, no dependency on the application. `normalize()` merges the noun/verb pair — the verb being the first following argument that *completes a known command name*, so a command option's value sitting between the two (`wpc plugin --page 2 list`) is stepped over rather than taken for the verb; only the application's own options are defined this early, which is why the position alone cannot be trusted. `normalizeCompletion()` does the same on the word list `_complete` receives, shifting the cursor index with it. Tested against the real command list in `tests/CommandLineTest.php`.
- **`src/Command/Listing.php`** — replaces Symfony's `list` with the docker-shaped screen behind `wpc`, `wpc list` and `wpc plugin`. Falls through to the parent for `--format`, `--raw` and `--short`, which are machine output. It goes through the router like everything else, so `--output=json` answers with `{usage, commands, options}` rather than the screen: under json the commands are the *runnable* names (`plugin list`, not the `plugin` noun the human screen groups them under), each with its aliases beside it.
- **`src/Command/ResourceCatalog.php`** — reads a collection off the `RegistryClient` (one page, or one record). Shared by `list` and by the picker `info` opens when it is given no slug.
- **`src/ResourceType.php`** — enum (`Plugin`/`Theme`) carrying every difference between the two command families (endpoint, upload field, header names, main file, and the `list`/`info` columns — a theme is shaped after the WordPress.org themes API: `downloaded`, `creation_time`, `description`, and an `author` *object*, which `Text::display()` shows by its `display_name` everywhere but `--output=json`).
- **`src/Command/Abstract*Command.php`** — one per verb (`List`, `Info`, `Build`, `Push`, `Manifest`, `Init`); they hold the shared logic. `AbstractResourceCommand` takes `(RegistryClient, OutputRouter, Runtime)` by constructor and passes **no name** to `parent::__construct()` — the `#[AsCommand]` attribute of the concrete class is what carries the name and the aliases. **`src/Command/{Plugins,Themes}/`** are thin subclasses declaring only their `#[AsCommand]` name, aliases and `ResourceType`:
  - `Init` (`<noun> init`), `Index` (`<noun> list`), `Info` (`<noun> info`), `Build`, `Push`, `Manifest`
  - **A required argument is never answered by a prompt.** `interact()` fills gaps only in `Init`, whose arguments are optional and whose whole point is asking. Anywhere else it would make the failure conditional on there being a terminal, and turn `info` with no slug into `list` under another name. `GrammarMigrationTest::testNoCommandAnswersItsOwnRequiredArgument` pins this by reflection.
- **`src/Command/SelfUpdate.php`** — `self-update` (`--check`, `--rollback`, `--major`), SHA-256-verified phar update. Crossing a major version is refused (exit 1) without `--major`: pipelines update themselves, and a major may rename what they call. The `Updater` comes from an injectable factory so the command is testable from source.
- **`src/Update/`** — `Updater` (download + checksum + backup/rollback), `UpdateChecker` (cached latest-version lookup for the passive notice), `Version` and `UpdateError`. **Versions decide before checksums** when `latest/manifest.json` is readable: a local build at or past the published release is up to date and never replaced (checksums alone only say "different", which "updated" a beta down to latest). `Version::release()` reads a `git describe` build (`1.0.2-57-g3156e95`) as its base tag, and treats anything else non-release (`@cli_version@`) as unknown, which falls back to the checksum comparison. **What is downloaded comes from the manifest too** when it pins a release: its `url` (an immutable versioned phar — the GitHub release asset since 2.1.0) is checked against its `sha256`, one object and its sum read from one document, instead of the mutable `latest/wpc.phar` + `latest/wpc.phar.sha256` pair, which CI cannot replace atomically. The pin is honoured only whole — a 64-hex sum *and* a plain HTTPS URL (no userinfo, port, dot segment, query or fragment) either on the manifest's own host or under `Updater::GITHUB_RELEASES` as `v<release>/<file>`, the public repository's release assets — and the manifest is read once per run; anything less falls back to the `latest/` pair, still published for older clients. Every HTTP failure becomes an `UpdateError` with a sentence ("No release is published at <url> yet (HTTP 403)." — the bucket answers 403 for a missing object), shown without the "Update failed:" prefix. Downloads follow redirects (GitHub answers an asset with a 302 to its storage host) over **HTTPS only**, at most five, without a `Referer`; the sum is checked on the last hop's bytes. Clients up to 2.0.0 only trust the manifest's host, so a GitHub pin sends them to `latest/` — keep publishing it. Tags are `vX.Y.Z` from 2.1.0 and Box stamps them verbatim: `Version::display()` drops one leading `v` wherever the running version is shown (`Application`'s constructor) and `Version::release()` wherever it is compared.
- **`src/Api/`** — `RegistryClient` (the interface the commands depend on: `get`, `upload`, `author`), `GuzzleRegistryClient` (the HTTP implementation) and `ApiError`. **No console type appears here**: progress is a callback, the same separation `BuildProgress` gives the builder. The client is built lazily on the first call, because the commands receive it before the repository URL is known. It was a singleton keyed on nothing — a second `instance()` with another URL silently returned the first client — which is why nothing that talked to the registry could be tested.
- **`src/Builder/`** — `Builder` / `Generator`: builds the plugin/theme zip archives (with `DirectoryIndex`, `EnsurePathTrait`). Progress is reported through the `BuildProgress` interface (`NullProgress` for JSON, `PlainProgress` for the historical `-v` file lines, `Tui\StepProgress` for the live step list) rather than written straight to the output.
- **`src/Tui/`** — the in-house terminal UI, built only on `symfony/console` (no extra runtime dependency):
  - `Environment` — the single place deciding whether a run may take over the terminal (also used by the update notice).
  - `RawMode` — stty raw mode with guaranteed restoration: `-isig` turns Ctrl+C into a readable byte (the only defence that works without ext-pcntl), plus a shutdown hook and a SIGINT/SIGTERM handler when pcntl is available.
  - `KeyReader` / `Key` / `KeyPress` — stdin bytes to keystrokes (CSI and SS3 sequences, UTF-8). Anything unrecognised maps to `Key::Unknown`, never to a key that acts.
  - `Screen` — the event loop, painting frames into a `ConsoleSectionOutput`; clears its block on exit so the caller can print the static rendering in its place. **The render callback must be a `function`, never an `fn`**: arrow functions capture by value, so a frame closing over mutable state redraws it as it was before the first keystroke — which is exactly how the text being typed came to be invisible. Objects are fine (the handle is what gets copied), plain values are not.
  - `Text` — width-aware (not byte-aware) cell sizing, wrapping, and HTML-ish value flattening, shared with `Results\BaseCommandResult`. **Two measures, and picking the wrong one misaligns the table**: `width()` is for chrome, a line the TUI assembled, where a tag is markup; `valueWidth()` is for data, where `<info>` is six columns of text the escaping will hand back to the terminal. Sizing a value with `width()` counted it as zero, padded the cell to full width on top and printed it at twice it. **Non-UTF-8 bytes are dropped at the door** (`utf8()`), because every `/u` pattern here returns null on the first invalid one and the casts turned that into an empty string — a wizard recap that disagreed with the file it had just written. **`hardSplit()` always consumes at least one character**, even one wider than the viewport: returning nothing left `wrap()` with a word it never shortened, and a terminal narrow enough to hit it (an emoji at width 1) froze the CLI in raw mode, where `-isig` means Ctrl+C is a byte nobody is left to read.
  - `Theme` — the accent colour, and only that. **It is only ever a background** (`selected()`, `caret()`): it is a button colour, dark by design with white on top, so using it as a foreground puts dark on dark in any dark terminal and the text disappears. Nothing the user types is coloured at all — that is content, and only the terminal's own foreground is readable by construction. It marks what the cursor is on (highlighted row, active tab, search field) and defaults to the dashboard's button colour (`--mat-sys-primary`, `#4433db`), overridable with `WPC_ACCENT_COLOR`; the text on it is picked from its luminance for a hex accent, and from a list of the light ones for a named accent — answering `white` for every name made `WPC_ACCENT_COLOR=white` a white-on-white band, with the cursor row indistinguishable from the rest. **The chrome stays on the terminal's palette** (`gray`, and Symfony's `<info>`/`<comment>`/`<error>`): a CLI sits inside someone else's colour scheme, and painting backgrounds over it fights the theme the user picked.

> **Where the brand colour comes from.** `Theme::BRAND_ACCENT` (`#4433db`) is the wp-content.io dashboard's button colour (its `--mat-sys-primary`); the docs site uses the same value. If the brand changes, it changes there first — do not pick a new accent here independently.
  - `Component/{DataTable,DetailView}` — the paginated list and the tabbed detail panel; `Prompt` and `StepProgress` cover the wizard and the build/push stages.
  - `Cancelled` — thrown by a `Prompt` on Escape, Ctrl+C or an input that ended, *never* returned. A wizard that read a cancelled question as "keep the default" would ask the next eleven and create the plugin anyway. `AbstractInitCommand` catches it and `execute()` writes nothing.

> **Two costs that made the wizard feel slow, both fixed, both easy to reintroduce.** `Screen` repaints on every keystroke, and `refreshDimensions()` used to shell out to `stty size` each time — a ~5 ms fork per character typed; the size is now trusted for 500 ms. And `RegistryClient::author()`, which pre-fills the wizard and runs *before* the first question, had no timeout: against an unreachable registry it inherited the OS connect timeout (~75 s on macOS) and the wizard simply appeared to hang. It now has its own 5-second budget, and the client a 10-second connect timeout — deliberately not a total one, since an upload may legitimately take minutes. `get()` does get a total budget (30 s): a host that accepts the connection and then says nothing would otherwise hang the TUI *inside* the raw-mode loop, where `-isig` has already turned Ctrl+C into a byte nobody is left to read.
>
> Note that per-frame rendering itself is cheap *only because* Symfony's `Application::run()` exports `COLUMNS`: without it `ConsoleSectionOutput` runs `stty -a` once per line rendered. Benchmarks that build a `Screen` outside `run()` will measure something 200× slower than reality.
- **`src/Results/`** — output formatting: `CommandOutput` exposes `human()`/`json()`; `InteractiveOutput` adds `interactive()` for the results worth navigating; `OutputRouter` picks the format *and the stream* (see "Streams and exit codes"); `CommandFailure` is the one failure shape. `SingleResult` is only navigable when a command opts in with `->navigable()`, so a push prints its confirmation instead of trapping the user in a panel. `ValueResult` (a bare value for a person, an object for a script — `manifest --get`), `StatusResult` (a sentence for a person, a payload for a script — `self-update`) and `ListingResult` (the command screen, or the commands as data) exist so the three commands whose human output is *not* a table still answer `--output=json` with one. **Every command goes through the router**, `init`, `self-update` and `list` included: writing straight to the output is how prose ended up on stdout under `--output=json`. **And every payload goes through `Results\Json`**: `json_encode()` returns `false` on malformed UTF-8 rather than throwing, and `(string) false` is an empty string — so one byte off a main file saved in ISO-8859-1 turned the answer into zero bytes on stdout, with an exit status of 0. Bad bytes are substituted there, the same call `Text::utf8()` makes on the rendering side.
- **`tests/`** — PHPUnit; `CommandContractTest` pins every command's name/aliases/arguments/options against `tests/fixtures/command-contract.json` (guard against accidental CLI-contract changes) and asserts the v1 names still resolve. `OutputContractTest` pins the other contract — which stream, which format, which exit code, on success and on every kind of failure. `GrammarMigrationTest` covers the migration promises end to end. Both use `tests/SplitOutput.php`, a console output whose two streams can be read separately, because `BufferedOutput` merges them and hides the whole point of writing to stderr. `tests/Fake/FakeRegistryClient.php` stands in for the registry, which is what makes `list`/`info`/`push`/`init` testable at all. The TUI is unit-tested without a terminal: components render to a string and are driven by synthetic `KeyPress`es.

> **Two things the suite depends on, both easy to break.** `tests/bootstrap.php` pins the colour mode (`Terminal::setColorMode(Ansi24)`): Symfony maps a hex colour down to whatever the terminal reports, so a frame assertion written against truecolor passed locally and failed in CI, where no `COLORTERM` is set. And an assertion holding a *literal* escape sequence pins the brand colour and the colour depth at once — derive it (`$this->rendered(Theme::selected(' Yes ')))` instead, or it silently stops testing anything the day either moves.
>
> `StringInput` does **not** go through `CommandLine::normalize()` — only the real argv does. A test driving a two-word command has to quote it: `new StringInput("'plugin list' --output=json")`.
>
> **An environment variable is set through `tests/EnvGuardTrait.php`, never `putenv()` alone.** The code reads `$_ENV`/`$_SERVER` first, so a `putenv()`-only test is shadowed by the same variable being genuinely exported — `WPC_ACCENT_COLOR=cyan composer test` used to fail seven of the ten theme tests, on exactly the machine of anyone using the documented knobs. The trait writes all three sources and restores all three; `composer test` has to stay green under `WPC_ACCENT_COLOR`, `WPC_NO_TUI`, `WPC_NO_DEPRECATED_WARNING` and `WPC_REPO_URL` being exported.

To add a resource command: add the verb logic to the matching `Abstract*Command`, or a new abstract command, then a thin subclass under `src/Command/{Plugins,Themes}/` listed in `Application::resourceCommands()`.

`bin/wpc` requires `$_composer_autoload_path ?? __DIR__.'/../vendor/autoload.php'`: installed with `composer global require`, it runs through Composer's proxy and the autoloader is the consumer's (`tests/BinTest.php`).

PSR-4 namespace: `WpContent\Cli\` → `src/`, with no `autoload.files`. The WordPress header block is parsed by `src/Wordpress/HeaderParser.php`; it used to be three functions declared in the global namespace under their WordPress names (`get_plugin_data()`…), which put the phar one `require` of a WordPress bootstrap away from a fatal redeclaration — in a tool people run inside WordPress projects.
